Cómo fluye una petición

El token lo genera y valida tu backend. El frontend solo lo guarda y lo reenvía. La seguridad nunca depende del navegador.

1 · Frontend (listo)LoginPage envía usuario y contraseña a POST /api/auth/login.
2 · Backend (tú)Compara con el hash bcrypt, rechaza inactivos, firma el token con el secreto del .env.
3 · Frontend (listo)AuthContext guarda { token, user }; client.js añade Authorization: Bearer a todo.
4 · Backend (tú)Middleware valida el token, extrae id y rol, y filtra en SQL según el rol. Sin permiso: 403.
5 · Frontend (completar)Dashboard cuenta tickets; Detalle muestra acciones por rol y llama a PATCH.

Qué recibes y qué implementas

Entregado Listo para usar

  • SQL Server 2022 en Docker con inicialización automática e idempotente.
  • Base MantenimientoDB con Usuarios, Contratos y Tickets, claves, CHECK e índices.
  • 6 usuarios con contraseña bcrypt (uno inactivo), 4 contratos, 17 tickets.
  • Login de base de datos mantenimiento_app con permisos mínimos.
  • Plantilla React que compila, con login funcional, rutas protegidas, cliente HTTP, tablas y Dockerfile.
  • Script tests/smoke.sh con los mismos 36 casos que usa el evaluador, y ejemplos de Dockerfile y conexión por stack en docs/ejemplos/.

Tú lo creas Backend

  • Conexión a SQL Server con mantenimiento_app (no sa) y consultas parametrizadas.
  • POST /api/auth/login con bcrypt y token; rechaza usuarios inactivos.
  • Middleware de autenticación y validación de roles en cada endpoint.
  • 3 GET de contratos y tickets filtrados por rol, 1 PATCH con reglas de negocio.
  • Errores con formato único y códigos 400 · 401 · 403 · 404 · 409 · 500.
  • Dockerfile y servicio en compose; configuración por variables de entorno.

Completar Frontend

  • Dashboard: contadores de tickets pendientes y en proceso.
  • Detalle: botones por rol y estatus, llamada al PATCH, refresco y errores 403/409.
  • Servicio frontend en compose con el build arg VITE_API_URL.
  • Probar con los tres roles y con tecnico04.

Ocultar un botón en React no es seguridad. El evaluador ejecuta bash tests/smoke.sh contra tu API: un técnico haciendo PATCH al ticket 102 debe recibir 403, cualquier PATCH al ticket 104 (finalizado) debe recibir 409 y tecnico01 debe recibir 403 en el contrato CON-004, donde no tiene tickets. Ejecuta el script tú mismo antes de entregar.

Antes de que empiece el tiempo

Estos pasos descargan imágenes y dependencias. Hazlos antes de iniciar el cronómetro; no forman parte de la prueba.

git clone https://github.com/sistemasbacros/prueba-tecnica.git
cd prueba-tecnica
docker compose up -d            # descarga SQL Server (~1.5 GB) y carga los datos
docker compose logs db-init     # "Base de datos inicializada correctamente"

cd frontend && npm install && npm run dev    # http://localhost:5173 (desarrollo)
# Ten listo el runtime de tu backend (Node, .NET SDK, Python, PHP+Composer…)
# Lee docs/ejemplos/ para tu stack y tests/README.md

Al entregar, el evaluador ejecutará docker compose up -d --build, luego bash tests/smoke.sh y abrirá el navegador.

Antes de entregar

  • docker compose down -v && docker compose up -d --build funciona desde cero.
  • bash tests/smoke.sh termina con FAIL: 0.
  • administrador, supervisor y tecnico01 entran; tecnico04 es rechazado.
  • El dashboard muestra 3 contratos activos, 6 pendientes y 3 en proceso para supervisor.
  • tecnico01 no ve CON-004, solo ve sus tickets y recibe 403 al modificar el ticket 102.
  • PATCH al ticket 104 responde 409. Petición sin token responde 401.
  • Ningún secreto en el código; existe .env.example.
  • README con todas las secciones y la pregunta de escalabilidad respondida.
  • Sin node_modules, vendor, bin/obj ni .env en el repositorio.
